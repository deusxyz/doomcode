# Acme: что это, чем отличается, что из него выросло

Обзор для проекта doomcode. Источники: исходники plan9port (`~/projects/plan9/src/cmd/acme`, `plumb`, `sam`), man-страницы acme(1), acme(4), plumb(7), plumber(4), sam(1), статья Р. Пайка «Acme: A User Interface for Programmers» (USENIX 1994), документация и обсуждения современных форков (ссылки в конце). Дата: 2026-10-04.

---

## 1. Определение в одну фразу

Acme — не редактор, а **гибрид оконной системы, оболочки и текстового редактора**, в котором единственный тип объекта на экране — редактируемый текст, а единственный механизм расширения — внешние программы, работающие с окнами через файловую систему.

Это ключевое отличие от всего класса «редакторов кода»: VS Code, Emacs, Vim, Zed — это редакторы с плагинами внутри процесса. Acme — это среда, где плагины снаружи, а редактор — лишь один из клиентов собственного API.

## 2. Принципы (из статьи Пайка и acme(1))

| # | Принцип | Как реализован |
|---|---|---|
| 1 | **Текст — это интерфейс.** Нет меню, кнопок, иконок, диалогов. «Any text can be in effect a menu item». | Любое слово в теге или теле окна — потенциальная команда (B2) или цель поиска/перехода (B3). Команды пишутся прямо в тег. |
| 2 | **Всё редактируемо единообразно.** Тег, тело, вывод команд, листинг каталога, окно ошибок — всё один и тот же текстовый виджет. | Единственное исключение: Acme сам восстанавливает служебные команды слева от `|` в теге. |
| 3 | **Три кнопки мыши, три семантики.** B1 — выделить, B2 — выполнить, B3 — «найти/получить» (look/acquire). | Одиночный клик B2/B3 расширяется до слова по контексту. Аккорды: B1+B2 = Cut, B1+B3 = Paste, B2+B1 = передать выделение аргументом команды. |
| 4 | **B3 как универсальный оператор перехода.** | Имя файла → открыть; `file:27`, `:/regexp/`, `file:/re/` → открыть и выделить адрес; `<stdio.h>` → include; иначе литеральный поиск в теле. Через plumber расширяемо до URL, картинок, man-страниц и т.п. |
| 5 | **Контекст — каталог из тега окна.** Нет глобального «текущего каталога» и «текущего проекта». | Относительные имена файлов и команды интерпретируются относительно каталога первого слова тега. |
| 6 | **Вывод программ — тоже текст в окне.** | stdout/stderr команды идут в окно `dir/+Errors` (создаётся при первой записи). `win` — оболочка в окне, 560 строк без графического кода. |
| 7 | **Тайлинг колонками, размещение автоматическое.** «Let the machine do the work». | Окна в колонках, новое окно ставится эвристикой, мышь сама перемещается к результату действия. Layout box: B1 чуть увеличить, B2 максимально, B3 захватить колонку. |
| 8 | **Нет click-to-type.** Ввод идёт в окно под мышью. | В plan9port есть опция `-b` (bartflag) для «обычного» фокуса по клику. |
| 9 | **Расширение — через файловую систему, а не через API библиотек.** | 9P-сервер, см. раздел 3. Клиенты пишутся на любом языке. |
| 10 | **Язык редактирования — структурные регулярные выражения Sam.** | Команда `Edit`: `x/re/ c/text/`, `g`, `v`, `s`, адреса `0,$`, `#n`, `/re/`. В 1994 году был внешним набором утилит, позже встроен. |
| 11 | **Минимализм как позиция.** Нет подсветки синтаксиса, автодополнения, конфигов, тем. | Пайк: Acme «mouse-based», Emacs — «keyboard-intensive and dauntingly complex». Расс Кокс на просьбы о подсветке: «Just say no». |

## 3. Архитектура и программный интерфейс

### 3.1 Файловая система окон (acme(4))

Корень сервиса `acme`:

```
index       одна строка на окно: id, длины тега/тела, флаги dir/dirty, тег
new/        доступ к любому файлу создаёт новое окно
log         блокирующий лог операций: new, zerox, get, put, del
cons        общий stdout/stderr всех команд (нет per-window cons!)
N/          каталог окна с id N:
  tag       тег (чтение любое, запись = append)
  body      тело (чтение любое, запись = append)
  addr      адрес в синтаксисе Sam; чтение возвращает #m,#n
  data      чтение/запись текста по addr (random access)
  xdata     как data, но чтение останавливается на конце addr
  ctl       управление: name, clean, dirty, dot=addr, addr=dot, show,
            nomark/mark (группировка undo), font, get, put, del, delete,
            dump/dumpdir (для восстановления сессии), limit=addr
  event     поток событий; пока открыт, B2/B3 перехватываются клиентом
  errors    append в dir/+Errors
```

### 3.2 Протокол событий (`event`)

Формат: `<origin><type> q0 q1 flag nchars text\n`.

- origin: `E` запись через body/tag, `F` через другие файлы, `K` клавиатура, `M` мышь.
- type: `I/D` вставка/удаление в теле, `i/d` в теге, `X/x` B2 в теле/теге, `L/l` B3, `R/r` Shift+B3.
- flag для X: 1 = встроенная команда, 2 = следует событие с развёрнутым словом, 8 = есть аккордный аргумент (ещё два сообщения).
- Клиент может вернуть событие обратно в `event`, и Acme выполнит его стандартно.

Это и есть «система расширений» Acme: клиент (например `win`, `Mail`, `acme-lsp`) открывает `event`, получает каждое нажатие B2/B3 и решает, обрабатывать ли его самому. Важная оговорка из статьи: изменения текста сообщаются **после факта**, клиент не может их отменить или отфильтровать (нельзя «выключить эхо»).

### 3.3 Plumber (plumb(7), plumber(4))

Отдельный сервис межпрограммной маршрутизации. Сообщение: `src, dst, wdir, type, attr, ndata, data`. Правила pattern/action в `$HOME/lib/plumbing`:

```
type is text
data matches '([.a-zA-Z¡-￿0-9_/\-@]*[a-zA-Z¡-￿0-9_/\-])('$addr')?'
arg isfile  $1
data set    $file
attr add    addr=$3
plumb to edit
plumb client $editor
```

B3 в Acme формирует plumb-сообщение с атрибутом `click=смещение`; plumber ищет самое длинное совпадение регулярки, покрывающее место клика. Порты `edit`, `web`, `image`, `postscript`, `man` и т.д. Это — обобщённый «go to definition / open link / open file», не зависящий от редактора.

### 3.4 Встроенные команды

`Abort Cut Del Delcol Delete Dump Edit Exit Font Get Incl Indent Kill Load Local Look New Newcol Paste Put Putall Redo Send Snarf Sort Tab Undo Zerox`, плюс префиксы `<` `>` `|` для фильтрации выделения через shell-команду. Всё остальное — внешние программы.

### 3.5 Внутреннее устройство (по исходникам plan9port)

- **Объём:** 15 810 строк C (с `edit.c`/`ecmd.c`/`regx.c` для языка Sam, `fsys.c`/`xfid.c` для 9P). Для сравнения: Go-порт в 9fans.net/go ~14 800 строк. Это очень компактно для редактора с собственным файловым сервером.
- **Текст:** `Rune` (UTF-32) в памяти; `Buffer` — массив блоков по 2 КБ рун с дисковым бэкингом (`Disk`, временный файл) и кэшем. То есть исходный Acme держал большие файлы вне ОЗУ.
- **Undo/redo:** транскрипт изменений `Elog`/`File`; `nomark` группирует изменения клиента в одну единицу undo.
- **Отрисовка:** библиотека `libframe` (один шрифт на окно, пропорциональный по умолчанию, табуляции в ширинах «0»). Нет атрибутов текста вообще: никакого цвета, жирности, подчёркивания на уровне модели. **Это главная архитектурная причина отсутствия подсветки**: модель текста не имеет слоя стилей.
- **Клавиатура (text.c):** стрелки (↑↓ в оригинале скроллят, не двигают курсор), PgUp/PgDn, Home/End, `^A ^E ^H ^U ^W`, `^F` автодополнение имени файла, `Esc` выделить набранное/вырезать выделенное, и на macOS `Cmd-C/X/V/Z/Shift-Z`. Всё. Нет ни одного способа выполнить команду или перейти по B3 с клавиатуры.
- **Процессная модель:** несколько потоков (мышь, клавиатура, файл-сервер, таймеры) через libthread-каналы.

### 3.6 Экосистема клиентов (как выглядят «расширения»)

| Программа | Что делает | Через что |
|---|---|---|
| `win` | shell в окне | event + body/addr/data |
| `awd` | обновляет тег win текущим каталогом | ctl name |
| `Mail` | почтовый клиент (1200 строк) | event |
| `acmego` | goimports/gofmt при Put | log + body |
| `Watch` | перезапуск команды при каждом Put в каталоге | log + окно `+watch` |
| `acme-lsp` | LSP-прокси: `L def refs fmt comp rename`, окно `/LSP/Diagnostics` | event + addr/data + plumber |
| `B`, `E`, `plumb` | открыть файл/адрес из командной строки | plumber |
| `adict`, `wintext`, `acmeevent`, `Netfiles` | словарь, дамп текста, отладка событий, удалённые файлы | разные |

Все они — отдельные процессы на любых языках, редактор о них не знает.

## 4. Чем Acme отличается от других в своём классе

| Аспект | Acme | Emacs/Vim | VS Code / Zed |
|---|---|---|---|
| Единица интерфейса | текст | буфер + minibuffer/командная строка | виджеты, панели, webview |
| Команды | любое слово на экране, B2 | клавиши, M-x, `:cmd` | палитра, меню, хоткеи |
| Навигация по коду | B3 + plumber (regex по тексту) | tags/LSP | LSP, индекс |
| Расширение | внешние процессы через FS | Lisp/Vimscript/Lua в процессе | JS extension host / WASM |
| Терминал | окно с текстом (`win`), вывод в `+Errors` | встроенные term/shell-режимы | встроенный эмулятор терминала |
| Раскладка окон | тайлинг колонками, автоматика | сплиты вручную | вкладки + сплиты |
| Клавиатура | минимум, мышь первична | клавиатура первична | смешанно, CUA |
| Подсветка/LSP/автоформат | нет / внешне / внешне | да / да / да | да / да / да |
| Конфигурация | почти нет (шрифт, колонки) | огромная | JSON + UI |
| Проект/workspace | нет понятия, контекст — каталог тега | по-разному | явный workspace |
| Размер ядра | ~16k строк | ~1M+ | ~1M+ |

Что сохранилось уникальным и ценным спустя 30 лет и чего нет ни у кого из «больших»:

1. **Исполняемый текст** и отсутствие разрыва между документацией, выводом команды и действием (guide-файлы: «найди пример, поправь, кликни»).
2. **Plumber** как внесистемный, настраиваемый пользователем маршрутизатор «что значит этот текст» — обобщение ссылок, go-to-definition и open-with.
3. **Файловый API** — любая программа на любом языке становится расширением за 50 строк.
4. **Контекст по каталогу тега** вместо «проекта»: редактор одинаково удобен для одного файла и для monorepo.
5. **Автоматическое размещение окон** и отсутствие вкладок.

## 5. Слабые места (подтверждено по коду и обсуждениям)

1. **Клавиатура.** Нет клавиатурного эквивалента B2 и B3. Аккорды с тачпада почти невозможны (аккорд 2-1 в plan9port невозможен вообще). ↑/↓ скроллят. Нет стандартных Ctrl-комбинаций вне macOS.
2. **Нет слоя стилей в модели текста** — подсветка, диагностика, inlay hints не на что «повесить». В оригинале это осознанный выбор, но технически это именно `libframe` с одним шрифтом.
3. **Нет понятия позиционных аннотаций** (маркеры ошибок, точки останова, git-blame). Диагностика LSP в acme-lsp — отдельное окно с `file:line`, что по-акмовски, но не inline.
4. **Один `cons` на все команды**, стандартный ввод команд — `/dev/null`. Интерактивные CLI работают только через `win`.
5. **События после факта**: расширение не может валидировать или трансформировать ввод (например, автозакрытие скобок, snippet-expansion требуют гонок с пользователем).
6. **Редактирование**: нет множественных курсоров, нет инкрементального поиска (поиск только через B3/Look/Edit), автоотступ примитивен (`Indent on`), нет автозакрытия, обёртки, column-mode.
7. **Нет конфигурации тем/клавиш**, цвета захардкожены (жёлтый тег, голубое тело).
8. **Шрифты** — только Plan 9 subfont-формат (в plan9port есть конвертация из TTF через fontsrv).

Выводы:

- **Никто не делал Acme с VS Code-расширениями.** Максимум — LSP.
- Anvil — самый близкий по UI к идее «осовременить», но без LSP и, по-видимому, без файлового API (т.е. потерял принцип 9).

- Клавиатурный эквивалент B2/B3 (Anvil: Ctrl-T/Ctrl-Enter; ad: модальные команды) **не ломает модель** Acme. Это главная подсказка для спецификации.

## 7. Совместимость с расширениями VS Code: оценка реализуемости

Факты:

- Расширение VS Code — npm-пакет на JS/TS, исполняемый в отдельном процессе **Extension Host** (Node.js). Связь с UI — типизированный RPC `MainThread*` ↔ `ExtHost*`.
- Поверхность API: `vscode.d.ts` — **21 239 строк**, 15 namespace'ов (`window, workspace, languages, commands, debug, scm, tests, notebooks, chat, lm, ...`) плюс ~180 proposed API. Плюс декларативная часть `package.json` (`contributes`: grammars, themes, languages, snippets, keybindings, views, configuration). Плюс Webview API (требует браузерный движок).
- **Eclipse Theia** — единственный не-форк, реализовавший API поверх своего UI: годы работы Red Hat/EclipseSource/TypeFox/Ericsson, и всё равно Monaco используется как текстовый виджет. Заявлена совместимость «с подавляющим большинством» расширений, не со всеми.
- **Zed явно отказался** реализовывать VS Code API (своя WASM-система).
- **Microsoft Marketplace закрыт** для сторонних продуктов по условиям использования; проприетарные расширения MS (C/C++, Pylance, C#, Remote) с 2025 проверяют хост и не работают в форках. Открытая альтернатива — **Open VSX** (1.0 в июне 2026), им пользуются VSCodium, Cursor, Theia, Positron.

Три возможных пути:

| Путь | Что получаем | Цена |
|---|---|---|
| **A. Форк Code-OSS** (как Cursor/Positron) | все расширения, Open VSX | Acme-принципы придётся впихивать в workbench, построенный на противоположных принципах (панели, вкладки, виджеты, Monaco). Мультимегабайтный Electron. Останется «VS Code с акме-скином». |
| **B. Свой редактор + собственная реализация extension host** (путь Theia) | большинство расширений | Реализация `TextEditor/TextDocument/decorations/selections/views/webview` поверх своего Acme-фрейма. Многолетний объём. Webview — встраиваемый Chromium/WebKit. |
| **C. Свой редактор + открытые протоколы**: LSP, DAP, TextMate-грамматики (`vscode-textmate`) и/или Tree-sitter, темы VS Code (JSON), сниппеты | все языковые функции: подсветка, автодополнение, диагностика, переходы, rename, форматирование, отладка; темы и грамматики берутся **из существующих .vsix без исполнения их кода** | Не работают расширения с собственным UI (webview, tree views, SCM, chat, тесты). Экспертная оценка покрытия ~80 % полезного, не измерялась. |

Для Acme-подобного редактора путь C естественен ещё и потому, что «родная» система расширений уже есть — файловый API. Он должен остаться первичным, а LSP/DAP — встроенными клиентами. Путь B можно оставить как необязательный этап после C: extension host как ещё один внешний процесс, говорящий с редактором через тот же файловый API.

## 8. Что надо решить, прежде чем писать спецификацию

1. **Клавиатурная модель.** Немодальная CUA + клавиатурные B2/B3 (как Anvil) или модальная (как ad/Kakoune)? Для «оказуаливания» — CUA; для «только клавиатура» надо спроектировать клавиатурную замену аккордам и перемещения курсора мыши к результату.
2. **Модель текста со стилями.** Вводим ли слой аннотаций (подсветка, диагностика, inlay hints, git) поверх текста? Если да — как это согласуется с принципом «всё — текст»? Вариант: аннотации не редактируемы и не входят в body, живут отдельным файлом `N/decor` в FS-API.
3. **FS-API: сохранить 9P-совместимость с acme(4)** (тогда работают win, acme-lsp, acmego, Watch, Edwood-экосистема) или спроектировать v2 (JSON-RPC/Unix socket) с мостом к 9P?
4. **Plumber**: встроить или использовать внешний plan9port plumber?
5. **Терминал**: окно-текст по принципу `win` (без ncurses-программ) или настоящий PTY-эмулятор как отдельный тип окна (нарушение принципа 2)?
6. **Технологический стек**: язык и графическая библиотека. Варианты: Go + Gio (Anvil), Go + duitdraw (Edwood), Rust + собственный GPU-рендер (как Zed), Rust + egui/iced. Если планируется путь B — Node.js придётся встраивать так или иначе.
7. **Отношение к VS Code-расширениям**: C, C → B, или A?
8. **Что считаем нарушением принципов, а что развитием.** Нужен явный список «инвариантов» Acme, которые проект обязуется не ломать.
