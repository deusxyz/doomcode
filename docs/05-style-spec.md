# Спецификация подсветки: файл `style` (черновик 1)

Цель: подсветка синтаксиса, диагностика LSP и прочая разметка текста в Edwood по-акмовски — слой поверх текста, вычисляемый внешней программой и передаваемый через файловый интерфейс acme(4). Дата: 2026-10-05.

## 1. Принципы

1. **Стили — слой, а не текст.** `body`, `data`, `xdata`, `event`, `addr` ничего не знают о стилях. Копирование, Edit, `win`, `acme-lsp` работают как прежде.
2. **Редактор не знает языков.** Кто и как вычисляет стили — дело внешней программы. Edwood только хранит отрезки, сдвигает их при правках и рисует.
3. **Совместимость acme(4).** Добавляются два файла в каталог окна: `style` и `changes`. Существующие файлы не меняются.
4. **Имена стилей, а не цвета.** Внешняя программа пишет `keyword`, `comment`, `error`; какие это цвета — решает тема редактора. Так один подсветчик работает со светлой и тёмной темами, а пользователь настраивает вид в одном месте.
5. **Один шрифт на окно** остаётся. Стиль — это цвет текста, цвет фона и подчёркивание. Жирный и курсив потребовали бы второго шрифта в кадре; это отдельное решение позже.

## 2. Файл `N/style`

Текстовый файл с правами чтения и записи в каталоге каждого окна (рядом с `addr`, `body`, `event`).

### 2.1 Чтение

Возвращает текущие отрезки, по одному на строку, отсортированные по началу, без перекрытий:

```
q0 q1 name
```

`q0`, `q1` — смещения в рунах (не байтах) в теле окна, как в `addr` и `event`; `[q0,q1)` полуоткрытый. `name` — имя стиля (раздел 4). Пустой файл — стилей нет.

### 2.2 Запись

Запись — последовательность строк, применяемая атомарно под блокировкой окна с одной перерисовкой:

| Строка | Действие |
|---|---|
| `q0 q1 name` | назначить стиль отрезку. Пересекающиеся существующие отрезки обрезаются или удаляются; новый побеждает. `q0 == q1` игнорируется |
| `clear` | удалить все отрезки окна |
| `clear q0 q1` | удалить стили в `[q0,q1)` (отрезки на границе обрезаются) |
| `# ...` | комментарий |

Смещения интерпретируются относительно тела **в момент записи**. Отрезки с `q1` за концом текста обрезаются; неизвестные имена стилей принимаются и хранятся, но рисуются цветом обычного текста (чтобы тема, добавившая имя позже, подхватила их без перезаписи).

Типичный цикл подсветчика: прочитать `body`, разобрать, записать `clear` и полный список отрезков одной записью. Для больших файлов — `clear q0 q1` и отрезки только изменившейся области.

### 2.3 Сдвиг при правках

Edwood сам поддерживает отрезки при вставках и удалениях, как поддерживает `q0/q1` выделения:

- вставка внутри отрезка расширяет его; вставка на границе `q1` — не расширяет (как курсор после слова не наследует его стиль);
- удаление сокращает или убирает отрезки; отрезок, полностью внутри удалённого диапазона, исчезает;
- `Get` (перезагрузка файла) очищает стили: тело заменяется целиком.

Так между правкой и следующей записью подсветчика текст остаётся раскрашен почти верно: сдвигается всё, что правее правки, а вновь набранное идёт стилем окружения или без стиля.

### 2.4 Zerox

Окна, созданные `Zerox`, разделяют текст, поэтому разделяют и стили: таблица отрезков принадлежит содержимому (`File`), а не окну. Запись в `style` любого из клонов меняет оба.

## 3. Файл `N/changes`: уведомления о правках без перехвата

Зачем он нужен. Единственный способ узнать о правках текста в acme(4) — открыть `event`. Но открытый `event` **перехватывает** B2 и B3: клиент обязан читать их и возвращать обратно, и так уже делает `acme-lsp`. Два клиента на одном `event` не работают: сообщения достаются одному из них. Подсветчик, живущий в каждом окне, не может быть вторым читателем `event`.

`changes` — файл только для чтения, поток сообщений об изменениях текста тела **без** перехвата кнопок и **с раздачей всем** читателям:

```
<origin><type> q0 q1 0 n text\n
```

Тот же формат, что у `event`, но только типы `I` (вставка) и `D` (удаление) для тела; origin `E`, `F`, `K`, `M` как в acme(4). Текст включается, если короче 256 рун, иначе `n = 0` и текст читается через `addr`/`data`. Чтение блокируется до следующего сообщения. Открытие `changes` ни на что в поведении окна не влияет. Открыть можно из нескольких процессов, каждый получает полную копию потока.

Этого достаточно для инкрементального подсветчика (tree-sitter принимает ровно такие правки), для «форматировать при Put» (`log` уже даёт `put`), и позже для линтера по мере набора.

## 4. Имена стилей и тема

Имена — произвольные слова `[a-z][a-z0-9._-]*`. Набор, который тема обязана знать (вдохновлён областями tree-sitter/TextMate, но короче):

| Имя | Назначение |
|---|---|
| `comment` | комментарии |
| `keyword` | ключевые слова |
| `string` | строки, символы |
| `number` | числа, константные литералы |
| `type` | типы |
| `function` | имена функций при объявлении и вызове |
| `variable` | идентификаторы (обычно без выделения) |
| `constant` | константы, перечисления, `true/nil` |
| `operator` | операторы |
| `punctuation` | скобки, запятые |
| `preproc` | директивы препроцессора, аннотации, `import` |
| `heading`, `emphasis`, `link` | разметка (Markdown, troff) |
| `error`, `warning`, `info`, `hint` | диагностика: фон-подсветка и подчёркивание |
| `match` | совпадения поиска, парная скобка |
| `diff.add`, `diff.del`, `diff.change` | состояние строк относительно git |

Иерархия через точку: если `keyword.control` неизвестен теме, берётся `keyword`; если и он неизвестен — обычный текст.

**Что задаёт стиль в теме:** цвет текста (обязательно или «как у текста»), цвет фона («как у окна» по умолчанию), подчёркивание (нет / сплошное). Диагностика по умолчанию — подчёркивание цветом уровня и слабый фон; подсветка синтаксиса — только цвет текста.

**Палитры.** В `theme` четыре палитры (`acme`, `vampira`, `solarizedlight`, `solarizeddark`), в каждой таблица стилей. Светлая: приглушённые цвета в духе Acme (комментарии серо-зелёные, ключевые слова тёмно-синие, строки коричневые, типы бирюзовые).

**Файл темы** (готово): `$EDWOOD_THEME`, иначе `$XDG_CONFIG_HOME/edwood/theme`, иначе `~/.config/edwood/theme`; накладывается на палитру при старте. Строки: `palette vampira` (база, если не задан `-palette`), `style keyword fg=#1f3a93 bg=#… line=#… underline|nounderline`, `style variable -` (убрать стиль), `text.back #ffffea mix #ffffff` и другие слоты палитры (`tag.*`, `text.*`: back high bord text htext tick; `ui.modbutton ui.colbutton ui.but2 ui.but3`). Цвета `#rgb`, `#rrggbb`, `#rrggbbaa`; `#` перед не-hex — комментарий. Команда `Theme` печатает действующие стили в синтаксисе файла, `Theme reload` перечитывает файл и перекрашивает окна (слоты палитры — после перезапуска), `Theme file`, `Theme slots`.

**Выделение.** Внутри выделения текст рисуется цветом `HText` на фоне `High`, как в Acme: выделение важнее стилей, и так оно всегда одинаково заметно. Подчёркивание диагностики под выделением сохраняется.

## 5. Отрисовка: что меняется в `frame`

Сейчас `frame` получает только руны (`Insert`, `InsertByte`), режет их на `frbox` по табуляциям, переводам строк и переносам, склеивает соседние box'ы (`mergebox`) и рисует все одним цветом (`drawtext`, `drawsel0`, `insertbyteimpl` используют `cols[ColText]`/`cols[ColBack]`).

Изменения:

1. `frbox` получает поле `Style uint8` (0 — обычный текст). `bxscan` режет box'ы ещё и на границах стилей; `mergebox` склеивает только box'ы одного стиля.
2. Новые методы интерфейса `Frame`:
   - `InsertStyled(r []rune, styles []uint8, p0 int) bool` — как `Insert`, но с параллельным массивом стилей на руну (память: 1 байт на видимую руну, кадр хранит только экран);
   - `Restyle(p0, p1 int, styles []uint8)` — переразбить и перерисовать диапазон без изменения текста (вызывается после записи в `style`);
   - `SetStyleTable(t []StyleColours)` — индекс стиля → цвета текста/фона и флаг подчёркивания, образы уже выделены темой.
   `Insert`/`InsertByte` остаются и означают стиль 0, так что `9term`, теги и колонки не меняются.
3. `drawtext`, `drawsel0`, путь вставки выбирают цвета по `box.Style`; подчёркивание рисуется линией в 1 px под box'ом после текста. Внутри выделения — цвета `High`/`HText` (раздел 4).
4. Тесты `frame` на разбиение по стилям и на `Restyle` добавляются к существующему набору box-тестов.

Индексы стилей — на уровне окна: таблица имён → индексов живёт в `Text`/`Window`, кадр видит только числа. Первая реализация делает `Restyle` через полную перезаливку видимой области (`fill`), оптимизация позже.

## 6. Хранение: `file.StyleTable`

Новый тип в пакете `file`, наблюдатель буфера (`BufferObserver`, как сам `Text`):

- хранит отсортированные отрезки `{q0, q1 int; name string}`;
- `Set(q0, q1, name)`, `Clear(q0, q1)`, `ClearAll()`, `At(q) (name, ok)`, `Range(q0, q1) []Span`;
- `Inserted`/`Deleted` сдвигают отрезки по правилам раздела 2.3;
- регистрируется у `ObservableEditableBuffer` тела окна при создании (`Window.Init`), поэтому у zerox-клонов таблица общая.

`Text.fill` и `Text.Inserted` берут стили для вставляемых рун из таблицы и зовут `InsertStyled`; остальное в `Text` не меняется.

## 7. Файловый сервер

- `dat.go`: `QWstyle`, `QWchanges`; `fsys.go` `dirtab`: `{"style", QTFILE, QWstyle, 0600}`, `{"changes", QTFILE, QWchanges, 0400}`.
- `xfid.go`: чтение `style` — сериализация таблицы; запись — разбор строк, применение под `w.Lock`, затем `Restyle` видимой части во всех `Text`-наблюдателях файла. Чтение `changes` — как `xfideventread`, но из отдельной очереди на каждый открытый Fid (раздача всем). Сообщения ставятся в очереди там, где `Text.Inserted/Deleted` формируют сообщения для `event`.
- `ctl` не меняется. Позже возможна строка `seq` в выводе `ctl` для проверки актуальности смещений подсветчиком; сейчас не нужна.

## 8. Программа `Syn`

Внешняя программа в репозитории justcode (`cmd/Syn`), по образцу `acmego`/`Watch`:

- следит за `log` (new, get, put, zerox) и за открытыми окнами;
- для окна с известным по имени файла языком читает `body`, строит дерево tree-sitter, пишет `clear` и отрезки в `style`;
- читает `changes`, применяет правки к дереву инкрементально (tree-sitter это умеет), перерисовывает затронутый диапазон с задержкой ~50–100 мс после последней правки;
- языки первой очереди: Go, C, Markdown, JSON, shell, затем Rust, Python, JavaScript/TypeScript;
- cgo здесь допустим: это внешняя программа, правило «без cgo в ядре» не нарушается. Библиотека — официальные биндинги `github.com/tree-sitter/go-tree-sitter` с грамматиками как Go-модулями.

Запуск: `Syn` в теге или из `run.sh`, как `acmego`. Выключение — `Del` на его окне или просто не запускать: Edwood без `Syn` остаётся монохромным Acme.

**Диагностика LSP (готово): `Diag`** (`cmd/Diag`). acme-lsp не меняется: он собирает диагностику в окно `/LSP/Diagnostics` строками `path:line.col,line.col: message`. `Diag` следит за этим окном через его `changes`, разбирает строки, переводит строку/колонку в руны по телу целевого окна и пишет `error` (или `warning`/`hint`, если это видно из текста сообщения: окно не несёт severity, флаг `-style` задаёт стиль по умолчанию) в `style` нужных окон, очищая только имена `error warning info hint`. Файлы, у которых диагностика пропала, очищаются. `Syn` в свою очередь чистит только свои имена (`clear q0 q1 comment keyword …`), поэтому подсветка и диагностика сосуществуют; это и есть ответ на вопрос о нескольких авторах. Проверено с gopls: `x` и `undefinedCall` подчёркнуты красным на розовом поверх подсветки; после правки метки едут вместе с текстом. Запуск: `acme-lsp -server '\.go$:gopls' -rootdir …` (в теге или из shell с тем же NAMESPACE), затем `Diag` в теге. Ограничения: severity угадывается по тексту; колонки LSP считаются в UTF-16, у нас — в рунах (расходятся только в строках с символами вне BMP); диагностика обновляется, когда её обновляет acme-lsp (по `Put`).

## 9. Порядок реализации

1. `frame`: `Style` в box'ах, `InsertStyled`, `Restyle`, `SetStyleTable`, тесты. Без этого остальное не видно.
2. `file.StyleTable` с тестами на сдвиг.
3. `theme`: таблица стилей для `acme` и `vampira`.
4. `Text`: стили в `fill`/`Inserted`; `Window.Init` регистрирует таблицу.
5. Файлы `style` и `changes` в `xfid.go`/`fsys.go`; проверка через `9p`: `echo '0 5 keyword' | 9p write acme/N/style`.
6. `Syn` для Go и Markdown; затем остальные языки.
7. Файл `theme` для пользовательских цветов.

Шаги 1–5 — в Edwood, ветка `style/frame` → `style/fs`; шаг 6 — в justcode `cmd/Syn`.

`style/frame` слита в `main` (fast-forward), `build.sh` собирает `bin/edwood` и `bin/Syn`, `run.sh` ставит `bin/` в PATH. Запуск подсветки: открыть `.go` или `.md`, выполнить `Syn` в теге (B2 или Ctrl-E). `Syn -all` красит и переменные/операторы/пунктуацию; `Syn -v` пишет в `+Errors`, что перекрасил.

Языки `Syn` по суффиксам: `.go`, `.c .h`, `.json`, `.sh .bash .zsh`, `.rs`, `.py`, `.js .mjs .cjs .jsx`, `.md .markdown`. Запросы подсветки — файлы `cmd/Syn/queries/*.scm`, встроенные через `go:embed`; это `highlights.scm` самих грамматик (MIT) с небольшими правками, перечисленными в `queries/README.md`. `Syn` инкрементален: держит копию текста и дерево, применяет сообщения `changes` к обоим (`tree.Edit`), после паузы перепарсивает с старым деревом и пишет `clear q0 q1` плюс отрезки только для затронутой области (правки ∪ `ChangedRanges`, расширенные до целых строк и целых захватов). Полная перечитка — при открытии, при сообщении, которое не укладывается в копию, при длинной вставке без текста с очередью позади, и при расхождении длины тела (проверяется по `ctl` каждые 200 правок). `Syn -dump файл` печатает полную разметку для отладки. Проверено на `devdraw.c` (32 177 рун): после серии правок разметка в редакторе совпала с полной рун в руну. Не поддержаны: TypeScript, Markdown внутри fenced-блоков, Plan 9 `rc`. Библиотека `9fans.net/go/acme` не открывает незнакомые имена файлов, поэтому `style` и `changes` открываются напрямую через `plan9/client`.

Решения по §10 (2026-10-05): `changes` — да; выделение скрывает цвета стилей, подчёркивание сохраняется; один файл `style`, `clear q0 q1 имя...` с фильтром имён; диагностика — подчёркивание плюс слабый фон; `Syn` на tree-sitter через cgo как внешняя программа.

## 10. Открытые вопросы (решены, см. §9a)

1. **`changes` как второй новый файл** — согласны? Альтернатива: разрешить нескольким читателям `event` и раздавать им копии; но это меняет семантику существующего файла (кто возвращает перехваченные B2/B3?), что нарушает инвариант совместимости.
2. **Выделение поверх стилей**: как в Acme (`HText` на `High`, стили скрыты) или сохранять цвет текста стиля на фоне `High`?
3. **Несколько авторов стилей** (подсветчик и диагностика): один слой с договорённостью «диагностика пишет только `error/warning/...` и чистит только их» — для этого `clear` получает необязательный фильтр по имени: `clear q0 q1 error warning`. Либо два файла `style` и `marks`. Предлагаю первое: один файл, `clear` с фильтром имён.
4. **Подчёркивание или фон** для диагностики по умолчанию?
5. **Tree-sitter через cgo в `Syn`** — приемлемо? Альтернатива без cgo — грамматики TextMate (нужна библиотека Oniguruma-регулярок, в Go её нет) или ручные regex-подсветчики на несколько языков.
